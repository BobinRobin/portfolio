Infrastructure · ~10 min

From a legacy server to a maintainable platform

Where it started

A server with no OS, no orchestrator, no conventions. It had to run two integration services: intake of electronic documents and a marking loop. No "deploy and forget": the system had to take traffic, survive failures and answer "what is happening right now" — via dashboards, not from me.

Layer 1: server and OS

Disks built for reliability and speed: mirroring plus striping (RAID). Server Linux, network and access configured. At this stage the point is not "install it" but to define how the system will be operated: who connects, from where, under which user, where logs live.

Layer 2: why K3s, not full Kubernetes

One node. Full Kubernetes on a single node burns resources on the control plane — apiserver, etcd, controllers. K3s gives the same API and ecosystem (Helm, ArgoCD) with a light control plane.

Honest trade-off: no control-plane HA on one node. If the node dies, the cluster does not revive itself. A deliberate choice at the current scale.

Layer 3: first services and manual deploys

Deploys were bash scripts: copy, restart, eyeball. Tolerable with two services and few changes. Then it hurt: manual builds, rollback from memory, "what is actually in prod" only if you remember.

Layer 4: CI/CD

GitLab CI took over builds: tests (pytest via uv), a multi-stage Dockerfile, publishing to a local registry. Builds stopped depending on a developer's machine.

Layer 5: observability

Before this, logs were read by hand via journalctl; there were no metrics. I assembled Prometheus (numbers), Grafana (dashboards), Loki (logs), introduced RED metrics — Rate/Errors/Duration — and business status counters.

Layer 6: GitOps

Imperative deploys left drift between Git and the cluster. Moved to GitOps: CI moves the tag in values.yaml, ArgoCD reconciles the cluster to Git, rollback is git revert.

# CI no longer deploys — it moves the tag in values.yaml
gitops:
  stage: gitops
  only: [main]
  script:
    - sed -i "s|^  tag: .*|  tag: \"$IMAGE_TAG\"|" deploy/helm/app/values.yaml
    - git commit -m "ci: deploy $IMAGE_TAG" || true
    - git push origin HEAD:main

Layer 7: security and resources

Secrets moved out of code and CI into Vault and Kubernetes Secret with least privilege. Containers run as non-root; requests/limits are explicit.

What it gave and what is next

Reproducible builds, declarative deploys, one-command rollback, secrets out of Git, transparent diagnosis. Honest limits: single-node and no verified recovery scenarios. Next: multi-node and regular backup/restore drills.

Integrations · ~10 min

Reliable enterprise integrations: four patterns

The rules of the game

An external system dictates the terms: file name, XML structure, code limit per document. You cannot fix it from your side, so all reliability goes in at the input.

Pattern 1. Idempotency from day one

A re-send of the same data must not create duplicates. We picked a bad key once: an attribute that repeated within one document — retries produced duplicates. The rule now: a business-unique key, checked before the insert.

# pseudocode: a gate before the database write
existing = db.exists(key=doc_key)
if existing:
    log.info("skip duplicate", key=doc_key)
    return
process_and_insert(doc)   # transaction commits only on success

Pattern 2. Contract-driven chunking

The external system accepts at most N codes per document. Split into parts with preserved ordering, so a retry of a failed part is deterministic — the same codes, not a reassembled document.

Pattern 3. Dry-run before go-live

External channels (FTP, callback, sales) are enabled one at a time. The pipeline runs without real sending first; channels go live sequentially when the loop runs clean.

Pattern 4. Data-level reconciliation

An external response is matched by exact identifier and file name, not by EAN or timing. We once searched by EAN while the system named files by order-line number — half a day lost.

Retries and timeouts

External services intermittently do not answer. Retry with exponential backoff and a bounded attempt count, otherwise you get a retry storm. Timeouts on every network call are mandatory — a hung request in a worker stalls the whole batch.

Common failures and what covers them

FailureCovered by
A retry duplicates recordsIdempotency with a unique key
A document exceeds the external limitChunking with preserved ordering
A pipeline error goes outsideDry-run, channels one at a time
Status does not match the real resultReconciliation by exact identifier
External service does not answerRetries with backoff and timeouts
Incidents · ~12 min

Incident investigation: from symptom to root cause

Why it is a skill

An engineer is defined not by a list of tools but by the ability to go from a symptom to the root. Tools are learned in a month; a way of reasoning is not.

The method in seven steps

1. Symptom and time.        What broke, since when.
2. Impact.                  Which loop, what is at risk.
3. Hypotheses top-down.     edge → service → queue → database.
4. Root cause.              What changed right before the failure.
5. Minimal fix.             With backup or revert.
6. Verify by data.          Record status or callback, not "seems fine".
7. Postmortem.              What, why, how to prevent.

Diagnostic tooling

journalctl -u  -n 200 --no-pager      # systemd service logs
kubectl -n  get pods,events             # state and events
kubectl -n  logs  --tail=200       # container logs
redis-cli XLEN                      # queue length
redis-cli XINFO STREAM              # consumer lag
psql -c "SELECT ..."                        # data state

Case 1: codes were not sent to FTP

Symptom: records in the DB, no XML sent, log line skip_no_pd=1000. The "broken pipeline" hypothesis failed — workers ran, the queue was empty. Moved to data: the product date was taken only from existing rows while new codes were inserted without it, though the dates sat in another table. The fix was not "restart" but extending the batch processor to look up the date from the right source.

Case 2: Grafana could not reach Loki

Symptom: the dashboard returned no logs. First instinct — fix Grafana or Loki. In reality it was a proxy conflict: moved Grafana to host network with a loopback datasource. The service is rarely the problem; data, network or config usually is.

Case 3: duplicates on retry

Symptom: re-processing created identical records. The "broken worker" hypothesis did not hold — the idempotency key repeated within a document. Fix: a business-unique key and a check before the insert, in one transaction.

Case 4: blockers before go-live

Symptom: a source audit found defects that blocked the rollout — async logic in the FTP poller (races and lost results), a mismatched callback contract, chunking-limit bypass, disabled idempotency, exposed secrets. Fixed one by one, with backups; secrets moved to a secret store.

Why method, not speed

Speed without method is blind restarts: the symptom vanishes for an hour and returns. Method makes the fix hit the root cause and the check confirm the result by data.

Alerting · ~8 min

Alerting to Telegram and eLink: knowing first

Why it matters

Dashboards are great when you watch them. Incidents do not ask whether Grafana is open. So I built a health check that walks the loop every 5 minutes.

What the health check probes

Simple facts, not "the server is alive": is the pod/service up, does the endpoint answer with the right code, is the database reachable, is the queue growing.

Two channels for different people

A short alert goes to Telegram: "service X is down". A detailed one goes to the corporate messenger eLink with full error context. eLink delivery via CLI, with a relay queue as a fallback.

Anti-spam

If a service is down for an hour, alerts should arrive once, not every 5 minutes. Statuses are persisted; a message is sent only on ok → broken and broken → ok transitions. Otherwise alerting becomes noise people stop reading.

Batch-job metrics

CronJobs live for minutes and die before Prometheus scrapes them. The fix is a Pushgateway: the job pushes its own metrics before exiting, so short-lived tasks get numbers, not just "completed".

Summary

Alerting is not "install a bot and relax" but a closed loop: check → channel → dedupe → react. Now I learn about problems first, not from a customer call.

Platform growth · ~8 min

How the platform grew: new loops and projects

Price-monitoring loop

A separate loop appeared: an hourly CronJob pipeline collects and processes data, a dedicated poller runs next to it, and Promtail ships logs. All of it in Kubernetes, deployed via the same GitOps, images in the local registry — a new service on an already-proven template.

ETL scheduler with DAGs

The sellout pipeline grew from "a script on cron" into a scheduler: every 5 minutes a job scheduler dispatches tasks across a DAG structure (Airflow approach). Dependencies between steps are visible; one step failing does not bring down the rest. Plus docker-compose for the ML stack, so the environment starts with one command.

Operations web monitor

For operations I built a lightweight web monitor: code statuses, queues, recent events — in one window instead of hopping across journals. Not a Grafana replacement, but a quick operational slice of "what is in the loop right now".

What this proves

When a platform works, new projects land on it in days, not weeks: take a ready CI → GitOps → alerting → observability template and fill it with business logic. That speed is the real sign of a mature platform.

AI Engineering · ~8 min

Working with AI agents: verify, do not trust

The agent's role

An agent accelerates, but does not remove my responsibility for the result. It helps in three places: task decomposition, context preparation, code generation. Then the human work starts.

Context decides everything

The quality of an answer depends on the quality of the context: runbooks, manifests, ADRs, a description of the current system state. No order in documentation — no precise answer.

Read-only audit

During incident reviews the agent runs read-only: it collects facts from logs, statuses and configs, but changes nothing. The agent proposes — the engineer applies.

What I check in generation

  • what exactly was generated and where the context came from;
  • what the code actually does, not what was intended;
  • does it pass tests and static analysis;
  • does it drag in secrets or unnecessary dependencies;
  • does it solve the task rather than "looking nice".

A side effect

Mandatory validation forces documentation to stay in order — otherwise there is nothing to feed the agent and nothing to check its output against. An agent does not "do the work for me"; it makes me do it more disciplined.
