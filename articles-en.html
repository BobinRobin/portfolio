Infrastructure · ~10 min

From a legacy server to a maintainable platform

Where it started

A server with no OS, no orchestrator, no conventions. It had to run two integration services: intake and processing of electronic documents, plus a marking loop. No "deploy and forget": the system had to take traffic, survive failures, and answer "what is happening right now".

The path was layered: hardware and OS first, then the platform, then the services, and only then automation, observability and security. Below is each layer, the reason, and what it fixed.

Layer 1: server and OS

The disk subsystem was built for reliability and speed: mirroring plus striping (RAID). A server Linux was installed; network and access were configured. The point at this stage is not "install it" but to define how the system will be operated: who connects, from where, under which user, where logs live.

Layer 2: why K3s, not full Kubernetes

One node. Full Kubernetes on a single node burns a noticeable share of resources on the control plane — kube-apiserver, etcd, controllers. K3s provides the same API and ecosystem (Helm, ArgoCD, CNI) with a light control plane and lower consumption.

Honest trade-off: for a single node there is no control-plane HA — if the node goes down, the cluster does not survive by itself. This is a deliberate choice at the current scale, not an oversight.

Layer 3: first services and manual deployment

The first versions were deployed with bash scripts: copy the artifact, restart, check by eye. It worked while there were two services and few changes. The pains showed up quickly: manual builds, no reproducibility, manual rollback from memory.

Layer 4: CI/CD

GitLab CI took over builds: tests (pytest via uv), a multi-stage Dockerfile, publishing images to a local registry. Builds no longer depended on a developer's machine. Deployment at this stage stayed imperative — kubectl patch from CI.

Layer 5: observability

Until then logs were read manually via journalctl; there were no metrics. I assembled Prometheus (numbers), Grafana (dashboards), Loki (logs), introduced RED metrics — Rate/Errors/Duration — and business status counters. Promtail was moved to journald with a systemd-unit label; otherwise Loki could not filter logs per worker.

The dashboards answer three questions: how much is processed, what is failing, what is queued. That is a different state from "the server is alive".

Layer 6: GitOps

Imperative deploys left drift between Git and the cluster: manual edits were overwritten by the next deploy, rollback hurt. We moved to GitOps:

# CI no longer deploys — it moves the tag in values.yaml
gitops:
  stage: gitops
  only: [main]
  script:
    - sed -i "s|^  tag: .*|  tag: \"$IMAGE_TAG\"|" deploy/helm/app/values.yaml
    - git commit -m "ci: deploy $IMAGE_TAG" || true
    - git push origin HEAD:main

# ArgoCD reconciles the cluster to this Git state

Now the truth is in Git; the cluster is derived from it. Rollback is a plain git revert, and every change is visible in repository history.

Layer 7: security and resources

Secrets were moved out of code and CI into Vault and Kubernetes Secret with least privilege: a service sees only its own secret. Containers run as a non-root user, and requests/limits are explicit — otherwise one service in a spike eats the node and drops the neighbours.

What it gave and what is next

The result: reproducible builds, declarative deploys, one-command rollback, secrets out of Git, transparent diagnosis. Honest limits of the current stage — single node and no verified recovery scenarios. Next maturity steps: multi-node with replica planning and regular backup/restore drills.

Integrations · ~10 min

Reliable enterprise integrations: four patterns

The rules of the game

An external system dictates the terms: file name, XML structure, the code limit per document, response requirements. You cannot "fix it from your side". So all reliability is built at the input — in your own pipeline, not in correspondence with the counterpart.

Pattern 1. Idempotency from day one

A re-send of the same data must not create duplicates. Sounds obvious, but in practice the key is easy to pick badly. We had a case: the key was an attribute that repeated within a single document — retries produced duplicates. The rule became simple: the key must be business-unique, and the check happens before the insert.

# pseudocode: a gate before the database write
existing = db.exists(key=doc_key)
if existing:
    log.info("skip duplicate", key=doc_key)
    return
process_and_insert(doc)   # transaction commits only on success

Pattern 2. Contract-driven chunking

The external system accepts at most N codes per document. Large documents are split into parts with preserved ordering. Why ordering: if one part goes through and the next fails, re-sending the second must be deterministic — the same codes in the same part, not a reassembled document.

# pseudocode: chunking with preserved ordering
for chunk in split_preserving_order(codes, limit=29999):
    filename = base + "_" + pad(index) + ".xml"
    send(filename, chunk)

Pattern 3. Dry-run before go-live

External channels (FTP, callback, sales) are enabled one at a time. First the pipeline runs without real sending: the same logs are written, the same metrics counted, but nothing goes outside. When data passes with no errors, channels are switched on sequentially. Slower, but errors are caught before they leave.

Pattern 4. Data-level reconciliation

An external response is matched by exact identifier and file name, not by EAN or timing. There was an incident: we searched for a response file by EAN while the external system named files by order-line number — half a day lost. Since then: the file name and schema of an external system are law, and everything is matched by that law.

Common failures and what covers them

FailureCovered by
A retry duplicates recordsIdempotency with a unique key
A document exceeds the external limitChunking with preserved ordering
A pipeline error goes outsideDry-run, channels one at a time
Status does not match the real resultReconciliation by exact identifier
External service does not answerRetries with exponential backoff and timeouts

Summary

A reliable integration is contract + idempotency + reconciliation + observability. If one link drops out of the chain, incidents become a matter of time, not chance.

Incidents · ~10 min

Incident investigation: from symptom to root cause

Why it is a skill

An engineer is defined not by a list of tools but by the ability to go from a symptom to the root. Tools can be learned in a month; a way of reasoning cannot. Below is the method that works for me, plus the commands I back it with.

The method in seven steps

1. Symptom and time.        What broke, since when.
2. Impact.                  Which loop, what is at risk.
3. Hypotheses top-down.     edge → service → queue → database.
4. Root cause.              What changed right before the failure.
5. Minimal fix.             With backup or revert.
6. Verify by data.          Record status or callback, not "seems fine".
7. Postmortem.              What, why, how to prevent.

Diagnostic tooling

journalctl -u  -n 200 --no-pager      # systemd service logs
kubectl -n  get pods,events             # state and events
kubectl -n  logs  --tail=200       # container logs
redis-cli XLEN                      # queue length
redis-cli XINFO STREAM              # consumer lag
psql -c "SELECT ..."                        # data state

Case 1: codes were not sent to FTP

Symptom: records exist in the DB, no XML sent, log line skip_no_pd=1000. The first hypothesis — "the pipeline is broken" — did not hold: workers were running, the queue was empty. We moved to the data. The product date was taken only from existing rows; new codes were inserted without it, though the dates sat in another table. The fix was not "restart" but extending the batch processor to look up the date from the right source.

Case 2: Grafana could not reach Loki

Symptom: the Grafana dashboard returns no logs. The first instinct is to fix Grafana or Loki. In reality it was a proxy conflict: Grafana was moved to host network with a loopback datasource. The moral repeats: "the service is broken" usually means data, network or config, not the service code itself.

Why method, not speed

Speed without method is blind restarts: the symptom can disappear for an hour and come back. The method guarantees the fix hits the root cause, and the check confirms the result by data, not by feeling. That is what separates operations from "administering by intuition".

AI Engineering · ~8 min

Human-in-the-loop: the discipline of working with AI agents

The agent's role

AI agents speed up work but do not remove the engineer's responsibility for the result. In my practice an agent is useful in three places: task decomposition, context preparation, and code generation. Then the human work starts.

Context decides everything

The quality of an agent's answer directly depends on the quality of the context. Runbooks, manifests, ADRs, and a description of the current system state are what we feed the agent. No order in documentation — no precise answer. Hence the rule: documentation is part of the infrastructure, not a "paper for later".

Read-only audit

During incident reviews the agent runs with read-only rights: it collects facts from logs, statuses and configs, but cannot change anything. Only a human applies changes after review. The same rule covers suggested patches: the agent proposes — the engineer applies.

Generation review checklist

  • what exactly was generated and where the context came from;
  • what the code actually does, not what was intended;
  • does it pass tests and static analysis;
  • does it drag in secrets or unnecessary dependencies;
  • does it solve the task rather than "looking nice".

Risks and how I close them

The main risk is blindly accepting generation: "the agent wrote it — so it works". That is closed by tests and code review. The second risk is secret leakage into generated code; scanning and the "secrets only in Vault" rule handle that. The third is losing the task context; a short task description in the commit and in the agent prompt covers it.

A side effect

Mandatory validation of generation forces you to keep runbooks and docs in order: otherwise there is nothing to feed the agent and nothing to check its output against. In the end, an AI agent does not "do the work for me" — it makes me do it more disciplined.
