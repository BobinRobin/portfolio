Infrastructure

The platform that runs integration services, ETL loops and an alerting system. Built from scratch, matured to GitOps, then grew: monitoring, Telegram and eLink alerts, an ETL scheduler.

Architecture

How it evolved

PlatformK3s, nginx, Redis (queues), PostgreSQL.
First servicesManual deployment via bash scripts.
CI/CDGitLab CI: tests, build, deploy.
ObservabilityPrometheus, Grafana, Loki. RED metrics.
GitOpsCI builds and moves the tag in Git, ArgoCD applies. Rollback = git revert.
SecurityVault, secrets out of Git, non-root containers, requests/limits.
AlertingHealth check every 5 minutes: Telegram (short) + eLink (detailed).
GrowthPushgateway for batch jobs, an operations monitor, an ETL scheduler, new cronjob loops.

Why this path

Each step fixed a concrete pain of the previous one:

  • K3s over full K8s — one node: a lighter control plane for the same API and Helm/ArgoCD ecosystem.
  • GitOps over kubectl patch — CI-only deploys left drift between Git and the cluster; ArgoCD reconciles to Git, rollback is revert.
  • Redis as a stream — a buffer between intake and processing; workers restart independently.
  • Vault / Secret over secrets in code — least privilege, rotation, audit.
  • RED metrics over raw CPU/RAM — a dashboard that answers "what is failing and what is queued".

Alerting: Telegram + eLink

A health check runs every 5 minutes and probes services, endpoints, database connectivity and queues. On a problem, two-channel alerts are sent: short ones to Telegram, detailed ones with error context to the corporate messenger eLink. Status changes are persisted so repeat alerts do not spam, and eLink delivery works via CLI or a relay queue.
