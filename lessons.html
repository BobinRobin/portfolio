Уроки и анти-паттерны

Список того, на что я уже наступал. Держу здесь, чтобы не повторять одни и те же грабли.

Идемпотентность

Ключ должен быть уникальным

Повторная обработка не должна дублировать записи. Сначала ключом был не уникальный атрибут — получали дубли. Теперь: идемпотентность с первого дня, ключ проверяем на уникальность.

Интеграции

Не искать файл по догадке

Искали файл ответа по EAN, а внешняя система называла его по номеру строки заказа. Правило: имя файла и структура внешней системы — закон, читать по точному имени.

Деплой

Внешние каналы — по одному

Не включать FTP/callback/Sales разом. Сначала конвейер работает в dry-run, потом каналы включаются по одному. Дороже по времени, но ошибки ловятся до внешней системы.

Наблюдаемость

Метрики — до инцидента

Без RED-метрик и логов чинишь вслепую. Минимум: rate/errors/duration и дашборд «что готово, что падает, что ждёт».

Инструменты

Один слой — один инструмент

Не заводить второй инструмент на ту же задачу, пока первый не упёрся в предел. Двойной рантайм (systemd + Kubernetes) — техдолг, сводить к одному.

Сеть

Прокси — частая причина «не видит»

«Grafana не видит Loki» оказалось конфликтом прокси на сервере. Проверяй network mode и адрес datasource, прежде чем чинить сам сервис.

Безопасность

Секреты не в Git

Креденшилы в коде и CI — критический риск. Выносить в Secret/Vault по принципу least privilege; контейнеры — не от root.

GitOps

Откат — это git revert

Императивный kubectl patch из CI оставлял расхождение «что в Git и что в кластере». GitOps: правда в Git, откат — revert.

Как этим пользоваться

Перед новым сервисом прогоняю чек-лист: идемпотентность на входе, dry-run внешних каналов, requests/limits, непривилегированный контейнер, RED-метрики, секреты вне Git. Это закрывает большую часть прошлых граблей.
