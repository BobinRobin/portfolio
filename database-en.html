Data layer

Two PostgreSQL instances with different roles, Redis as an event transport, separate schemas for prod and test.

PostgreSQL: two distinct jobs

Business data

TBase — distributed PostgreSQL

Marking and document-flow data lives on TBase, a PostgreSQL fork that adds distributed tables and horizontal scaling.

  • Distributed fork on a PostgreSQL 10.0 base (64-bit)
  • Chosen for table growth: sharding while keeping the classic SQL interface
Tooling

PostgreSQL 16 (local)

A separate local instance serves GitLab and internal CI/CD tooling.

  • Version: PostgreSQL 16 (Ubuntu)
  • Isolation: a tooling failure does not touch the business loop

Redis — queues and events

Redis is used as an asynchronous event transport (Streams), not just a cache. Incoming messages are written to a stream; workers read and process them. This buffers intake from processing and smooths load spikes.

Multi-environment via schemas

Prod and test live in separate schemas of the same database. Switching is done in code (contextvars + middleware in Python), so integrations can be tested without duplicating the database infrastructure.

The TBase version and topology are described in general terms, without internal addresses or hostnames.
