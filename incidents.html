Инциденты и их разбор

Реальные сбои в боевом контуре: симптомы, проверенные гипотезы, первопричина, постоянное исправление и предотвращение повтора. Каждый кейс — по методу STAR.

1. Sticker: новые коды не уходили на FTP

S: Новые sticker-записи писались в базу со статусом «получено», но XML на FTP не отправлялся. В логе — skip_no_pd=1000.

T: Найти причину отсева и вернуть коды в пайплайн без дублей.

A: Проследил путь кода: дата продукта бралась только из существующих строк, а новые коды вставлялись без неё, хотя даты были в отдельной таблице. Дописал batch-процессор: для кодов без даты ищем её в дополнительном источнике и пишем обратно. Заодно исправил подсчёт признака «есть работа».

R: Пайплайн снова подтягивает данные и отправляет XML; расхождение «есть данные — нет отправки» устранено.

2. Идемпотентность: неверный ключ дублировал записи

S: Повторная обработка приводила к дублям: ключ идемпотентности не был уникален для документа.

T: Сделать повторную отправку безопасной — «повторный пост не должен дублировать запись».

A: Определил действительно уникальный ключ вместо исходного и перевёл дедупликацию на него; проверил сценарий повторного поста.

R: Повторный ввод перестал создавать дубликаты; контур стал безопасным к ретраям.

3. Grafana не видела Loki из-за прокси

S: После сборки стека наблюдаемости Grafana не могла достучаться до Loki.

T: Найти причину на уровне сети/конфигурации, не меняя сами сервисы.

A: Локализовал конфликт прокси на сервере: перевёл Grafana на host network, datasource через loopback. Параллельно перевёл сборщик логов на journald с меткой systemd-юнита.

R: Логи доступны в Grafana; метки дали быстрый поиск по конкретному воркеру.

4. Блокеры production-rollout (критические дефекты)

S: При доведении контура до боевого запуска аудит исходников выявил дефекты, блокировавшие rollout.

T: Устранить первопричины до включения внешних каналов.

A: Исправил: асинхронная логика в FTP-опросе (гонки и потеря результата), несогласованный контракт callback, обход лимита чанкинга, отключённую идемпотентность, открытые секреты (вынес в секрет-хранилище). Патчи применялись с бэкапами и проверкой исходного состояния.

R: Контур доведён до безопасного состояния; внешние каналы включаются по одному (dry-run), а не разом.

5. Наблюдаемость «с нуля»

S: Долгое время метрик не было, логи воркеров читали вручную.

T: Построить единое место для метрик и логов.

A: Собрал Prometheus (числа) + Grafana (дашборды) + Loki (логи): RED-метрики rate/errors/duration, бизнес-каунтеры статусов, два SRE-дашборда.

R: Диагностика перестала быть «вслепую»: инциденты видны по метрикам и логам, а не по ручному чтению.

Уроки повторяются: идемпотентность — с первого дня, ключ — действительно уникальный; dry-run перед включением внешних каналов; наблюдаемость — не роскошь; один слой — один инструмент.
