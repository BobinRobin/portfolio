Инфраструктура

От legacy-сервера к управляемой платформе

Исходное состояние — сервер без ОС, без платформы, без наработанных соглашений. Задача — два боевых сервиса документооборота и маркировки. Я шёл слоями, и каждый следующий слой закрывал конкретную боль предыдущего.

Почему K3s, а не полный Kubernetes. Один узел: полноценный kube-apiserver, etcd и контроллеры съедали бы заметную долю CPU/RAM впустую. K3s даёт тот же API, Helm и ArgoCD, но лёгкую управляющую плоскость. Минус — нет HA на уровне control plane, это осознанный компромисс для single-node.

Почему GitOps, а не kubectl patch из CI. Деплой прямо из пайплайна оставлял расхождение «что в Git и что реально в кластере»: правки на сервере терялись при следующем деплое. ArgoCD приводит кластер к состоянию из Git, а откат — это обычный git revert. Цена — нужен отдельный контроллер, но это покупает воспроизводимость и аудит изменений.

# CI больше не деплоит — он двигает тег в values.yaml
gitops:
  stage: gitops
  only: [main]
  script:
    - sed -i "s|^  tag: .*|  tag: \"$IMAGE_TAG\"|" deploy/helm/app/values.yaml
    - git commit -m "ci: deploy $IMAGE_TAG" || true
    - git push origin HEAD:main

# ArgoCD синхронизирует кластер с этим Git-состоянием

Наблюдаемость до инцидента. RED-метрики (Rate/Errors/Duration) вместо голых CPU/RAM: дашборд отвечает на «что падает и что ждёт», а не рисует железо. Promtail перевели на journald с меткой unit — иначе в Loki логи нельзя было фильтровать по конкретному воркеру.

Итог: декларативный деплой, откат одной командой, секреты вне Git, прозрачная диагностика. Следующий шаг зрелости — multi-node и backup/restore с проверкой восстановления.

Интеграции

Надёжные enterprise-интеграции: паттерны, которые пережили сбои

Внешняя система диктует правила: имя файла, структура XML, лимит кодов на документ. Это не «поправить со своей стороны», поэтому надёжность закладывается на входе. Четыре паттерна.

1. Идемпотентность с первого дня. Повторный POST не должен дублировать запись. Ключ должен быть бизнес-уникальным: однажды ключом был атрибут, который повторялся в одном документе — получили дубли. Решение — перейти на действительно уникальный идентификатор строки документа и проверять его до вставки.

# псевдокод: gate перед записью в БД
existing = db.exists(key=doc_key)
if existing:
    log.info("skip duplicate", key=doc_key)
    return
process_and_insert(doc)   # транзакция коммитится только при успехе

2. Чанкинг по контракту. Внешняя система принимает не более N кодов в одном документе. Большие документы дробятся на части с сохранением порядка, чтобы повторный ретрай был детерминированным: та же порция — тот же набор кодов.

3. Dry-run перед боем. Внешние каналы (FTP, callback, sales) включаются по одному. Сначала конвейер работает без реальной отправки, метрики и логи смотрят на вхолостую, и только потом каналы включают по очереди. Дороже по времени, но ошибки ловятся до того, как уйдут во внешнюю систему.

4. Сверка на уровне данных. Ответ внешней системы ищется по точному совпадению идентификатора и имени файла, а не по EAN или таймингу. Однажды искали файл ответа по EAN, а система называла его по номеру строки заказа — полдня потерь. С тех пор: имя файла и структура внешней системы — закон.

Инциденты

Расследование инцидента: от симптома к первопричине

Инженера отличает не знание инструментов, а умение идти от симптома к корню. Порядок, который у меня сложился.

1. Симптом и время.        Что именно сломалось, с какого момента.
2. Влияние.                Какой контур затронут, что под риском.
3. Гипотезы сверху вниз.   edge → сервис → очередь → база.
4. Первопричина.           Что изменилось непосредственно перед сбоем.
5. Минимальное исправление. С бэкапом/ревертом.
6. Проверка по данным.     Статус записи или callback, а не «вроде заработало».
7. Postmortem.             Что, почему, как не допустить повторно.

Кейс: коды не уходили на FTP. Симптом — новые записи есть в базе, но XML не отправляется, в логе skip_no_pd=1000. Гипотеза «сломан пайплайн» не подтвердилась: дело было в данных. Дата продукта бралась только из существующих строк, а новые коды вставлялись без неё, хотя даты лежали в отдельной таблице. Исправление — не «перезапустить», а дополнить batch-процессор поиском даты из правильного источника.

Кейс: Grafana не видела Loki. Первое желание — чинить сервис. На деле — конфликт прокси на сервере: Grafana перевели на host network, datasource — через loopback. Мораль: «сервис сломан» чаще всего означает данные, сеть или конфигурацию.

AI Engineering

Human-in-the-Loop: дисциплина работы с AI-агентами

AI-агенты ускоряют, но не снимают с инженера ответственность. Полезная роль агента — декомпозиция, сбор контекста и генерация кода. Дальше начинается работа человека.

Что проверяю всегда: что именно сгенерировано и откуда взят контекст; что код делает на самом деле, а не что задумывалось; проходит ли тесты и статический анализ; не тянет ли секреты и лишние зависимости; решает ли задачу, а не «выглядит красиво».

Read-only аудит. При разборе инцидентов агент запускается с правами только на чтение и собирает факты из логов, статусов и конфигов. Изменения вносит только человек после ревью.

Побочный эффект: обязательная проверка генерации заставляет держать runbook'и и документацию в порядке — иначе агенту нечего скормить и не с чем сверять результат. Human-in-the-loop — это не «понаблюдать за агентом», а дисциплина валидации.
