Инфраструктура

От legacy-сервера к управляемой платформе

Исходное состояние — сервер без ОС, без платформы, без наработанных соглашений. Задача — два боевых сервиса документооборота и маркировки. Я шёл слоями, и каждый слой закрывал конкретную боль предыдущего.

Почему K3s, а не полный Kubernetes

Один узел: полноценный kube-apiserver, etcd и контроллеры сжигали бы CPU/RAM впустую. K3s даёт тот же API, Helm и ArgoCD при лёгкой управляющей плоскости. Минус — нет HA на уровне control plane; это осознанный компромисс для single-node, а не «не успели».

Почему GitOps, а не kubectl patch из CI

Деплой прямо из пайплайна оставлял расхождение «что в Git и что реально в кластере»: ручные правки на сервере терялись при следующем деплое. ArgoCD приводит кластер к состоянию из Git, а откат — обычный git revert. Цена — отдельный контроллер, но это покупает воспроизводимость и аудит изменений.

# CI больше не деплоит — он двигает тег в values.yaml
gitops:
  stage: gitops
  only: [main]
  script:
    - sed -i "s|^  tag: .*|  tag: \"$IMAGE_TAG\"|" deploy/helm/app/values.yaml
    - git commit -m "ci: deploy $IMAGE_TAG" || true
    - git push origin HEAD:main

# ArgoCD синхронизирует кластер с этим Git-состоянием

Безопасность и ресурсы — с первого дня

Секреты из кода и CI вынесены в Vault/Secret по принципу least privilege: сервис видит только свой секрет. Контейнеры работают от непривилегированного пользователя, а requests/limits заданы явно — иначе один сервис в пике съест узел и уронит соседей.

Наблюдаемость до инцидента

RED-метрики (Rate/Errors/Duration) вместо голых CPU/RAM: дашборд отвечает на «что падает и что ждёт», а не рисует железо. Promtail перевели на journald с меткой unit — иначе в Loki логи нельзя было фильтровать по конкретному воркеру.

Итог: декларативный деплой, откат одной командой, секреты вне Git, прозрачная диагностика. Честная граница: single-node и отсутствие проверенных бэкапов — следующий шаг зрелости (multi-node + backup/restore drills).

Интеграции

Надёжные enterprise-интеграции: паттерны, которые пережили сбои

Внешняя система диктует правила: имя файла, структура XML, лимит кодов на документ. Это не «поправить со своей стороны», поэтому надёжность закладывается на входе. Четыре паттерна, которые выдержали реальные сбои.

1. Идемпотентность с первого дня

Повторный POST не должен дублировать запись. Ключ должен быть бизнес-уникальным: однажды ключом был атрибут, который повторялся внутри одного документа — получили дубли. Решение — перейти на действительно уникальный идентификатор строки документа и проверять его до вставки.

# псевдокод: gate перед записью в БД
existing = db.exists(key=doc_key)
if existing:
    log.info("skip duplicate", key=doc_key)
    return
process_and_insert(doc)   # транзакция коммитится только при успехе

2. Чанкинг по контракту

Внешняя система принимает не более N кодов в одном документе. Большие документы дробятся на части с сохранением порядка, чтобы повторный ретрай был детерминированным: та же порция — тот же набор кодов.

3. Dry-run перед боем

Внешние каналы (FTP, callback, sales) включаются по одному. Сначала конвейер работает без реальной отправки, метрики и логи смотрят вхолостую, и только потом каналы включают по очереди. Дороже по времени, но ошибки ловятся до внешней системы.

4. Сверка на уровне данных

Ответ внешней системы ищется по точному совпадению идентификатора и имени файла, а не по EAN или таймингу. Однажды искали файл ответа по EAN, а система называла его по номеру строки заказа — полдня потерь. С тех пор: имя файла и структура внешней системы — закон.

Инциденты

Расследование инцидента: от симптома к первопричине

Инженера отличает не знание инструментов, а умение идти от симптома к корню. Порядок, который у меня сложился, и команды, которыми я его подкрепляю.

# гипотезы сверху вниз по стеку
journalctl -u  -n 200 --no-pager      # логи systemd-сервиса
kubectl -n  get pods,events             # состояние и события
kubectl -n  logs  --tail=200       # логи контейнера
redis-cli XLEN                      # длина очереди
redis-cli XINFO STREAM              # отставание потребителей
psql -c "SELECT ... "                       # состояние данных

Кейс: коды не уходили на FTP. Симптом — записи в базе есть, XML не отправляется, в логе skip_no_pd=1000. Гипотеза «сломан пайплайн» не подтвердилась: дело было в данных. Дата продукта бралась только из существующих строк, а новые коды вставлялись без неё, хотя даты лежали в отдельной таблице. Исправление — не «перезапустить», а дополнить batch-процессор поиском даты из правильного источника.

Кейс: Grafana не видела Loki. Первое желание — чинить сервис. На деле — конфликт прокси: Grafana перевели на host network, datasource через loopback. Мораль: «сервис сломан» чаще всего означает данные, сеть или конфигурацию.

AI Engineering

Human-in-the-Loop: дисциплина работы с AI-агентами

AI-агенты ускоряют, но не снимают с инженера ответственность. Полезная роль агента — декомпозиция, сбор контекста и генерация кода. Дальше начинается работа человека.

Чек-лист проверки генерации:

  • что именно сгенерировано и откуда взят контекст;
  • что код делает на самом деле, а не что задумывалось;
  • проходит ли тесты и статический анализ;
  • не тянет ли секреты и лишние зависимости;
  • решает ли задачу, а не «выглядит красиво».

Read-only аудит. При разборе инцидентов агент запускается с правами только на чтение и собирает факты из логов, статусов и конфигов. Изменения вносит только человек после ревью.

Побочный эффект: обязательная проверка генерации заставляет держать runbook'и и документацию в порядке — иначе агенту нечего скормить и не с чем сверять результат. Human-in-the-loop — это не «понаблюдать за агентом», а дисциплина валидации.
